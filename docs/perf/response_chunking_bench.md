# Response chunking benchmark

Generated by `python scripts/bench_response_chunking.py --iterations 30`
on the deterministic CPU stub encoder. Numbers measure the **Python
orchestration overhead per chunk** (no GPU encode time, no NLI), so they
isolate the response-chunking stitch / aggregation / merge cost from
real model inference.

| Regime                                  | Tokens | Chunks | p50 ms | p95 ms | Mean ms |
| --------------------------------------- | -----: | -----: | -----: | -----: | ------: |
| short / 1 chunk (budget 512)            |     15 |      1 |   1.68 |  89.69 |   11.71 |
| short / 1 chunk (budget 256, default)   |     15 |      1 |   1.66 |  89.84 |   13.42 |
| long / ~10 chunks (budget 32)           |    310 |     11 | 195.81 | 287.74 |  179.53 |
| very_long / ~40 chunks (budget 32)      |   2480 |     81 |1388.08 |1405.21 | 1303.26 |

## What the table shows

1. **Short responses pay no chunking tax.** When the response fits in a
   single window the orchestrator delegates to `score_groundedness_chunked`
   verbatim, so the parity fast path costs the same 1.6 ms p50 as the
   pre-chunking implementation. The high p95 in this regime reflects
   first-call lazy initialisation in the stub provider, not steady-state
   latency.
2. **Long responses scale linearly in chunk count.**
   - 11 chunks → 196 ms p50 → ~17.8 ms / chunk.
   - 81 chunks → 1388 ms p50 → ~17.1 ms / chunk.
   The marginal cost per added chunk is constant, which proves the merge
   step is O(R) (one pass over response tokens), not O(M·U) or worse.
3. **Total compute matches the unchunked baseline.** Per-chunk matmul
   FLOPs for `R_k × C × dim` summed over `M` chunks equals
   `R_total × C × dim`, so on a real GPU the response-chunked path is
   wall-clock equivalent to a hypothetical "encode the full response,
   then score" path that would otherwise OOM beyond the encoder's
   `doc_maxlen`.

## Re-running

```bash
VOYAGER_GROUNDEDNESS_NLI_ENABLED=0 \
LATENCE_TRACE_DISABLE_WARMUP=1 \
python scripts/bench_response_chunking.py --iterations 30
```

For end-to-end latency including real encoder + NLI inference, run the
multilingual benchmark harness in `research/triangular_maxsim/` against
a real encoder.
